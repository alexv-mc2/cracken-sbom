# BSI TR-03183-2 v2.1.0 in cracken-sbom

[BSI TR-03183-2 v2.1.0](https://www.bsi.bund.de/dok/TR-03183-en) (2025-08-20)
sets the content of an SBOM for products sold in Germany and for the Cyber
Resilience Act. Since about 2026-02-20 only CycloneDX 1.6 or later (or SPDX
3.0.1 or later) is accepted (§4, §7). cracken-sbom writes CycloneDX 1.6 JSON.

This page lists, field by field, where each value comes from. The tool fills
in what it can read or compute locally. It never invents a value: anything it
cannot know is listed in `quality.json` under `tr_gaps`.

## SBOM fields (§5.2.1, §5.2.3)

| Field | CycloneDX 1.6 | Source |
|---|---|---|
| Creator of the SBOM (e-mail, else URL) | `metadata.manufacturer` (`contact[].email`, `url[]`) | `--manufacturer-email` / `--manufacturer-url` / `--manufacturer-name` or `--metadata` |
| Timestamp | `metadata.timestamp` | local clock, UTC |
| SBOM-URI | `serialNumber` | new random `urn:uuid` per run |
| No vulnerability information (§3.1) | no `vulnerabilities` key | enforced; generation fails otherwise. VEX data goes into a separate file |

## Primary component (product, §3.2.1)

`metadata.component` with `bom-ref` `cracken-product`.

| Field | Source |
|---|---|
| Name, version | `--product-name`, `--product-version`; else the npm lockfile project; else the target's file or folder name and `--target-id` (reported in `tr_gaps`) |
| Creator | the SBOM creator above |
| Distribution licence | `--product-license` (SPDX expression), `acknowledgement: concluded` |
| SHA-512 of the deployable file | `externalReferences[type=distribution].hashes`; the target file for `oci-archive`, `docker-archive` and `firmware-image`, `--artifact` for directory targets |
| File name | `bsi:component:filename` of the same file |
| Executable / archive / structured | see the taxonomy table below |
| Dependencies | the product depends on every component that no other component depends on (and on any component a cycle would leave unreachable) |

## Each component (§5.2.2, §5.2.4)

| Field | CycloneDX 1.6 | Source |
|---|---|---|
| Creator | `manufacturer` | package metadata (`author`, `publisher`, `supplier`). Only the name by default; e-mail and URL with `--component-contacts` |
| Name, version, purl, CPE | `name`, `version`, `purl`, `cpe` | Syft |
| Distribution licences | `licenses[]` with `acknowledgement` | Syft's detected licences, written as `declared`. With `--conclude-licenses` they are written as `concluded` |
| SHA-512 of the deployable component | `externalReferences[type=distribution].hashes` | npm `package-lock.json` / `npm-shrinkwrap.json`, `yarn.lock` v1 and `bun.lock` integrity values; the file itself for binaries, kernels and Java archives found inside a scanned directory |
| File name | `bsi:component:filename` | the tarball name from the lockfile, or the cataloged file's name; never a path |
| Executable, archive, structured | `bsi:component:executable`, `:archive`, `:structured` | taxonomy table below |
| Dependencies | `dependencies[]` | Syft's graph; every component has an entry, leaves an empty one |

### Taxonomy values

Property names and values are those of the
[BSI CycloneDX property taxonomy v0.1.2](https://github.com/BSI-Bund/tr-03183-cyclonedx-property-taxonomy).
The mapping follows TR-03183-2 §8.1.4–8.1.7 (Table 7):

| Component | executable | archive | structured |
|---|---|---|---|
| Package-manager package (deb, rpm, apk, opkg, npm, PyPI, Maven, Cargo, NuGet, ...) — like the rpm package in Table 7 | non-executable | archive | structured |
| Binary found by content (Syft binary classifiers, ELF/PE package notes, Linux kernel), and libraries found inside binaries by version string | executable | no archive | unstructured |
| Go or Rust binary with build information ("binary with integrated SBOM") | executable | no archive | structured |
| Java archive | executable | archive | structured |
| Operating-system component (logical) | non-executable | no archive | structured |
| Product: `firmware-image` | executable | no archive | unstructured |
| Product: `oci-archive`, `docker-archive` | non-executable | archive | structured |
| Product: `rootfs`, `dir`, `npm`, `python` | executable | archive | structured |

## Completeness (§5.2.2)

`compositions[0].aggregate` covers the product and every component:

| Value | When |
|---|---|
| `complete` | only for `npm` targets with a `package-lock.json` / `npm-shrinkwrap.json` v2 or v3, when every graph reference survived minimization |
| `incomplete` | Syft reported a dependency graph, but nothing proves it is whole |
| `unknown` | Syft had no dependency graph for the target |

The metadata property `cracken:tr:graph-source` (`lockfile`, `engine`, `none`)
records which case applied.

## Licences: declared or concluded

TR-03183-2 asks for the *distribution* licences (`concluded`) and, where they
exist, the *original* licences (`declared`). What a scanner finds in package
metadata is what upstream declared. Calling it the distribution licence is the
manufacturer's statement, so the tool writes `declared` unless you pass
`--conclude-licenses`. sbomqs scores the default lower; that is intended.
The product's own licence (`--product-license`) is always `concluded`.

## What the tool does not do

- It does not fetch anything: no registry metadata, no licence texts, no hashes
  from the network.
- No SHA-512 for packages whose lockfile only carries SHA-256/SHA-1 (pip,
  Poetry, uv, Cargo, Go) or for installed OS packages, whose package archive is
  not on disk. These are counted in `tr_gaps`.
- `pnpm-lock.yaml` and Yarn berry `checksum` values are not read (berry hashes
  Yarn's cache archive, not the published tarball).
- No source-code URI, security.txt URL or effective licence (§5.2.4, §5.2.5).
- No signature (§8.1.15).

## Checks in CI

Every SBOM generated by the test suite is checked by:

1. the vendored CycloneDX 1.6.1 JSON schema (`tests/validate-schema.py`);
2. `cyclonedx validate --input-version v1_6 --fail-on-errors` (cyclonedx-cli v0.33.1);
3. `tests/tr_check.py`: taxonomy values, exactly-once rules, file names, SHA-512
   format, licence acknowledgement, every component reachable from the product,
   `complete` only for a lockfile graph, no `vulnerabilities`;
4. `sbomqs compliance --bsi-v21` (sbomqs v2.1.3) via `tests/sbomqs_check.py`:
   the SBOM-level checks must pass; the reports and scores are kept in the test
   output folder.
